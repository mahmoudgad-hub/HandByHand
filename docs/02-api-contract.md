`hbhd` — خدمة Go. القراءة الوحيدة المعتمَدة لهذا العقد هي هذا الملف؛ الكود يتبعه ولا
يسبقه.

**النطاق:** بوابة ولي الأمر **وتطبيق المركز**. منذ 2026-09-03 صار PostgreSQL مصدر
الحقيقة وتوقّفت أوراكل — **D-26**.

---

## الأساس

| | |
|---|---|
| القاعدة | `http://localhost:8090` محليًا · `API_PORT` يغيّرها ولا شيء في الكود يثبّتها |
| الترميز | `application/json; charset=utf-8` — والطلبات كذلك |
| الوقت | كل لحظة **UTC** بصيغة RFC 3339. التحويل لتوقيت القاهرة **عرض فقط** |
| النسخة | `/api/v1` — ما عدا `/healthz` و`/readyz` |
| المصادقة | `Authorization: Bearer <token>` — في الترويسة فقط، **أبدًا في رابط** |

**ولا بيانات شخصية في رابط أو معامل استعلام.** رقم الجوّال يُرسَل في جسم `POST`،
ومعرّف الطفل رقمٌ لا يكشف شيئًا بذاته لأن السياسة هي التي تقرّر من يراه.

---

## اللغة — لا نص عربي في هذه الطبقة

الـ API يرجع **رموزًا**، والصياغة العربية في ملفات ترجمة Angular. راجع D-11.

```json
{ "error": { "code": "WRONG_CODE", "request_id": "9f2c4a1b7e0d3355" } }
```

`request_id` موجود في كل رد وفي ترويسة `X-Request-Id`. هو الرابط بين شكوى مستخدم
وسطر في اللوج — ولا يحمل أي معلومة عن الحساب.

---

## الدخول — طلبان، ولا قرار في أيٍّ منهما

القرارات كلها في `hbh.request_otp` و`hbh.verify_otp`: طول الرمز، صلاحيته، سقف
المحاولات، مهلة إعادة الإرسال، وما يحدث عند آخر محاولة خاطئة. طبقة Go تترجم الإجابة
إلى HTTP ولا تضيف قاعدة.

### `POST /api/v1/auth/otp/request`

```json
{ "mobile": "01012345678" }
```

**الرد — `202 Accepted`، وهو نفسه لكل رقم:**

```json
{ "status": "SENT", "expires_in_seconds": 900, "resend_in_seconds": 60 }
```

**هذا التطابق هو خاصية أمنية، لا كسل.** `hbh.request_otp` تعرف الفرق وتقول
`NOT_REGISTERED`، وتمريرها كان سيحوّل شاشة الدخول إلى أداة للسؤال: «هل هذا الشخص عميل
لدى مركز علاج أطفال؟». الرقم غير المسجّل، والحساب الموقوف، والرقم المسجَّل الذي طلب
رمزًا قبل ثانية — كلها ترجع الرد نفسه بالحالة نفسها.

الرفض الوحيد هنا هو `400 VALIDATION` لرقم لا يطابق `MOBILE_PATTERN`، وهو حكم على
**شكل** المدخل قبل أن يعرف الخادم شيئًا عن صاحبه.

> **في التطوير فقط** يُضاف `dev_code` إلى الرد لأنه لا توجد بوّابة رسائل بعد.
> `config.Load` **ترفض تشغيل** عملية غير تطويرية والعلم مرفوع، ولهذا الرفض اختبار وحدة.

### `POST /api/v1/auth/otp/verify`

```json
{ "mobile": "01012345678", "code": "418302" }
```

**`200 OK`:**

```json
{ "token_type": "Bearer", "token": "…", "expires_at": "2026-09-03T04:12:55Z" }
```

**الرفض:**

| الحالة | `code` | متى |
|---|---|---|
| `401` | `WRONG_CODE` | رمز خاطئ — ومعه `fields.attempts_left` |
| `401` | `EXPIRED` | انتهت صلاحية الرمز |
| `401` | `NO_PENDING_CODE` | لا رمز حيّ — **وكذلك لرقم غير مسجَّل**، عمدًا |
| `423` | `TOO_MANY_ATTEMPTS` | استُنفدت المحاولات والحساب أُقفل |
| `423` | `USER_LOCKED` | الحساب موقوف |

`423` وليس `401` للحالتين الأخيرتين: `401` تدعو العميل للمحاولة ثانية، والباب هنا
مغلق حتى يفتحه إنسان.

`attempts_left` ينقص فعلًا ويبقى ناقصًا. `verify_otp` **لا ترفع استثناءً** لرمز خاطئ
لأن PostgreSQL بلا معاملات مستقلّة: الاستثناء كان سيلغي زيادة العدّاد ويجعل التخمين
مجانيًا.

### `POST /api/v1/auth/logout`

يحتاج توكنًا. يرجع `204`. **الإلغاء فوري** — الطلب التالي بالتوكن نفسه يرجع `401`.
هذه هي الخاصية التي رفض D-10 التنازل عنها.

## البوابة

كل ما تحت هذا العنوان يحتاج `Authorization`. بلا توكن: `401 UNAUTHENTICATED`.

### `GET /api/v1/me`

```json
{
  "user":   { "user_id": 12, "center_id": 1, "username": "…", "full_name_ar": "…",
              "user_type": "GUARDIAN", "status": "ACTIVE" },
  "center": { "center_id": 1, "code": "HBH", "currency_code": "EGP",
              "time_zone": "Africa/Cairo", "weekend_days": [5, 6] },
  "permissions": ["PORTAL.VIEW", "REPORT.VIEW", "REQUEST.SUBMIT"]
}
```

`weekend_days` و`currency_code` و`time_zone` **بيانات، لا افتراضات في الكود**. مركز
في بلد آخر يحتاج صفًّا، لا إصدارًا.

`permissions` مصفوفة دائمًا — `[]` وليس `null` — حتى لا يختلف عميلٌ يفحص «بلا صلاحيات»
عن عميلٍ يفحص «الحقل غائب».

### `GET /api/v1/me/contact` · `PATCH /api/v1/me/contact`

```json
{ "email": "…", "city": "…" }
```

**الحقلان اللذان يملكهما وليّ الأمر**، ونظيرهما — ما ليس هنا — هو النصف المهمّ:

| الحقل | ولي الأمر يعدّله؟ |
|---|---|
| `email` · `city` | نعم |
| `mobile` | **لا — هو هويّة الدخول نفسها.** رمز الدخول يصل إليه، فمن يستطيع تغييره من هاتف مسجَّل الدخول ينقل الحساب إلى رقم آخر — وكذلك من أمسك هاتفًا غير مقفول ثلاثين ثانية |
| `full_name_ar` · `national_id` | لا — تُراجَع أمام مستند في الاستقبال، والاسم هو المكتوب على السجلّ السريري والفواتير |
| `relationship` | لا، الآن: ادّعاء عن صلة هذا الشخص بطفل، وهل يجوز أن يُقرّ به صاحبه قرارُ عمل لم يُتَّخذ بعد |

**والحقلان يُرسلان معًا دائمًا، والفارغ يمسح العمود.** البديل — «الغائب يعني اتركه» —
يمنح وليّ الأمر طريقًا لإضافة عنوان ولا طريق لحذفه.

**ولا معرّف في المسار.** السياسة على `hbh.guardians` ترجّع صفّ المتصل وحده، والكتابة
تمرّ عبر `hbh.update_own_guardian_contact` التي تأخذ **وسيطين** — فلا وسيط ثالث يُرسَل.
سياسة `UPDATE` تستطيع أن تقول أي **صفوف**، ولا تستطيع أن تقول أي **أعمدة**؛ ففتح الصفّ
كان سيفتح معه رقم الجوّال. وحساب بلا صفّ وليّ أمر يحصل على `404`، لا على صفّ فارغ.

**وليس في القائمة:** «رقم بديل» لا عمود له في السكيما أصلًا — إضافته قرار لا مهاجرة،
لأنها تحتاج مكانًا على شاشة الاستقبال أيضًا وإلا صار رقمًا يُخزَّن ولا يُتَّصل به.
و«التفضيلات» لا مفهوم لها في السكيما بعد.

### `GET /api/v1/children`

**مسار واحد لجمهورين.** ولي الأمر يرى أطفاله؛ وموظّف يحمل `CHILD.VIEW_ALL` يرى
أطفال المركز. **السياسة** هي التي تقرّر، ولا يوجد مسار ثانٍ لتطبيق المركز — المسار
الثاني كان سيصير موضعًا ثانيًا تعيش فيه القاعدة.

`?q=` بحث بالاسم العربي **مطويًّا** (`normalize_arabic` — «احمد» تجد «أحمد») أو بـ`child_no` ·
`?status=` الوضع في المركز · `?archived=true` يشمل المؤرشف · `?limit=` و`?page=` (بادئة من ١).
والرد يحمل `total` و`limit` و`offset` — فشاشة تقول «صفحة ١ من ٤» بدل أن تخمّن.

**والمؤرشف مستبعَد افتراضيًا.** هذا ليس تجميلًا: حين كانت القائمة تتجاهل `active_flg`،
كانت أرشفة طفل **لا تُحدث أثرًا تراه الشاشة** — فاستنتج الكونسول أن الأرشفة فشلت،
وأعاد المحاولة فأخذ `404` من نداءٍ ثانٍ على صفّ مؤرشف بالفعل.

**و`status` غير `active_flg`.** الأول وضع الطفل في المركز (متخرّج مثلًا — وسجلّه حيّ)،
والثاني هل السجلّ نفسه مؤرشف. سؤالان مختلفان، والشاشة تحتاجهما معًا.

```json
{ "children": [ { "child_id": 41, "child_no": "CH-00021", "full_name_ar": "…",
                  "birth_date": "2020-03-15", "gender": "M", "status": "ACTIVE",
                  "link": { "relationship_code": "FATHER", "is_primary": true,
                            "can_view_live": false, "can_view_reports": true } } ] }
```

`link` غائب لموظّف — الموظّف يصل عبر صلاحية، لا عبر صلة قرابة.
`can_view_live` افتراضه `false` في السكيما: مشاهدة طفل داخل جلسة علاجية أخطر ما يفعله
هذا النظام، وتُمنَح عمدًا أو لا تُمنَح.

### `GET /api/v1/children/{child_id}`

**هذه النقطة هي سبب وجود المرحلة.**

ولي أمر يعدّل الرقم في الرابط يصل إلى نفس المعالِج تمامًا. **لا شيء في المعالِج يقارن
أي شيء**: السياسة على `hbh.children` تنادي `hbh.can_access_child()`، والصف لا يُسلَّم،
فيرى المعالِج «صفر صفوف» — وهي بالضبط ما يراه لطفل غير موجود أصلًا.

| | |
|---|---|
| `200` | الطفل، بنفس شكل عنصر القائمة |
| `404 NOT_FOUND` | غير موجود **أو ليس طفلك** — الاثنان رد واحد |

**`404` وليس `403`، وهذا قرار لا اختصار.** `403` كانت ستؤكّد أن الطفل موجود، والأرقام
يسهل المرور عليها واحدًا واحدًا.

كل قراءة ناجحة هنا تُسجَّل `READ`، وكل رفض يُسجَّل `DENY` — المشغّلات لا ترى `SELECT`،
فإمّا تُسجَّل هنا أو لا تُسجَّل في أي مكان.

# السجلّ السريري

خمس نقاط معلَّقة على الطفل، وكلها **ترث الحاجز نفسه**: المخزن يثبت أن الطفل مرئي
**داخل نفس المعاملة** التي يقرأ فيها. معاملتان كانتا ستقرآن لقطتين مختلفتين، فيُسحَب
الوصول بين الفحص والقراءة وتُسلَّم البيانات رغم ذلك.

ولي أمر يطلب طفلًا ليس طفله يأخذ **`404`** على كل واحدة منها، ويُسجَّل الرفض باسم
المسار — لا قائمة فارغة، لأن القائمة الفارغة تخبر من يمشي على الأرقام أنه أصاب طفلًا
حقيقيًا بلا بيانات.

| النقطة | ترجع |
|---|---|
| `GET /api/v1/children/{child_id}/appointments` | المواعيد، الأحدث أولًا |
| `GET /api/v1/children/{child_id}/sessions` | الجلسات التي حدثت فعلًا |
| `GET /api/v1/children/{child_id}/plans` | الخطط، ومعها أهدافها وآخر قياس لكل هدف |
| `GET /api/v1/children/{child_id}/reports` | تقارير التقدّم |
| `GET /api/v1/children/{child_id}/notes` | ملاحظات الجلسات **المنشورة للأسرة** |
| `GET /api/v1/reports/{report_id}` | تقرير واحد بجسمه ولقطة أهدافه |

## سلّم الرؤية — وهو **كل** ما تدور حوله هذه الدفعة

ولي الأمر لا يرى كل شيء عن طفله، وهذا مقصود ومُنفَّذ في السياسات لا هنا:

| الشيء | يصل لولي الأمر متى |
|---|---|
| **ملاحظة جلسة** | `visibility = 'PARENT'` **و** ليست مسودّة **و** لها معتمِد |
| **تقرير تقدّم** | `status = 'PUBLISHED'` |

**كل ملاحظة تُولد `INTERNAL`.** وصولها للأسرة فعلٌ منفصل ومقصود من شخص يملك
`NOTE.PUBLISH`. الملاحظة الداخلية عن طفل ولي الأمر نفسه — على نفس الجلسة، بقلم نفس
الأخصائي — **لا تصل إليه**.

**ومسودّة التقرير عن طفله هو تُجيب `404`** كأنها لم تُكتب قط. لأن معرفة ولي الأمر بوجود
تقرير قبل أن يقرّر الأخصائي نشره هي في ذاتها تسريب.

## المواعيد والجلسات

```json
{ "appointments": [ { "appointment_id": 12, "appointment_no": "APT-2026-00007",
  "starts_at": "2026-09-07T07:00:00Z", "ends_at": "2026-09-07T07:45:00Z",
  "status": "CONFIRMED", "cancel_reason": null,
  "service":   { "service_id": 3, "name_ar": "تخاطب", "kind_code": "SPEECH", "color_hex": "#3B7A9E" },
  "therapist": { "therapist_id": 2, "full_name_ar": "…", "title_ar": "أخصائي أول" },
  "room":      { "room_id": 1, "name_ar": "غرفة ١" } } ] }
```

**نافذة اختيارية:** `?from=&to=&limit=` — و`from`/`to` **لحظات RFC 3339، لا تواريخ
مجرّدة**. تاريخ مجرّد كان سيُجبر هذه الطبقة على تقرير أي منتصف ليل يقصده — القاهرة أم
UTC — وهو قرار عمل لا يُكتب في الكود. العميل يعرف منطقته ويرسل لحظة. `limit` بين ١ و٥٠٠.

**ما لا يخرج:** `note_ar` على الموعد و`abort_reason` على الجلسة. كلاهما نصّ حرّ يكتبه
الموظّفون، **وليس لأيٍّ منهما سلّم اعتماد** كالذي تملكه ملاحظة الجلسة. محجوبان حتى
يصير لهما واحد — وهذا افتراض مُعلَن، لا حذف بالسهو.

## الخطط والأهداف

```json
{ "plans": [ { "plan_id": 4, "title_ar": "خطة الربع الأول", "status": "ACTIVE",
  "start_date": "2026-06-01", "end_date": null,
  "service": {…}, "therapist": {…},
  "goals": [ { "goal_id": 9, "title_ar": "نطق صوت السين", "baseline_pct": 30,
               "target_pct": 80, "status": "OPEN", "sort_order": 10,
               "latest_pct": 62, "latest_measured_on": "2026-08-24",
               "measurement_count": 2 } ] } ] }
```

الأهداف تأتي من `hbh.v_goal_progress`، وهو **عرض `security_invoker`** — فالسياسات تنطبق
على المتصل تمامًا كقراءة مباشرة. عرضٌ بلا `security_invoker` كان سيعمل بصلاحيات مالكه
ويسلّم أهداف كل مركز لأي أحد.

## التقارير

```json
{ "report_id": 3, "report_no": "RPT-2026-00002", "title_ar": "تقرير الربع الأول",
  "period_start": "2026-06-01", "period_end": "2026-08-31", "status": "PUBLISHED",
  "published_at": "2026-09-01T09:12:00Z", "summary_ar": "…",
  "goals_snapshot": [ { "goal_id": 9, "title_ar": "…", "latest_pct": 62 } ] }
```

`goals_snapshot` تُؤخَذ **مرة واحدة عند النشر** ولا تُقرأ الأهداف حيّةً بعدها. فالتقرير
يعرض ما كان صحيحًا لحظة توقيعه، ولا يستطيع قياسٌ لاحق أن يعيد كتابة مستند قرأته الأسرة.

## يومٌ ليس لحظة

`birth_date` و`start_date` و`period_start` و`latest_measured_on` **أيام تقويمية**:
`"2020-03-15"`، لا `"2020-03-15T00:00:00Z"`. الثانية يقرأها عميل في القاهرة على أنها
الرابع عشر — نفس عيب الساعتين الذي وُجد D-5 لإزالته، معادًا إدخاله عند حافة النظام.

اللحظات — `starts_at` و`published_at` و`created_at` — تبقى **UTC** بصيغة RFC 3339.

# البرنامج المنزلي والطلبات

| النقطة | ترجع |
|---|---|
| `GET /api/v1/children/{child_id}/activities` | التمارين المسنَدة، ومعها الالتزام في آخر سبعة أيام |
| `GET /api/v1/children/{child_id}/activity-log` | الأيام التي أبلغت عنها الأسرة |
| **`POST`** `…/activities/{child_activity_id}/log` | تسجيل يوم |
| `GET /api/v1/children/{child_id}/requests` | طلبات الأسرة وقرارات المركز عليها |
| **`POST`** `…/{child_id}/requests` | فتح طلب |

**أول كتابتين في هذه الخدمة**، وكلٌّ منهما تُفحَص **مرّتين**:

الطبقة هنا تتأكّد أولًا أن الطفل مرئي — وهذا لأجل **الإجابة** لا لأجل الأمان: بدونه
يأخذ من يمشي على الأرقام `403` على طفل ليس طفله، و`403` تؤكّد أن الطفل موجود.
ثم تفحص دالة الداتابيز من الداخل، وفحصها **أضيق**: `submit_request` تشترط أن يكون
المتصل **وليّ أمر** الطفل فعلًا — والموظّف الذي يحقّ له قراءة الطفل ليس كذلك، فيأخذ
`403` عن حقّ.

```json
POST …/activities/12/log     { "log_date": "2026-09-03", "done": true, "note_ar": "…" }
POST …/requests              { "kind_code": "RESCHEDULE", "appointment_id": 41, "body_ar": "…" }
```

| الحالة | متى |
|---|---|
| `201` | سُجّل · فُتح الطلب |
| `409 ALREADY_LOGGED` | اليوم مسجَّل بالفعل — الداتابيز **ترفض ولا تكتب فوقه**: نقرة ثانية أرجح كثيرًا من تغيّر رأي، والكتابة فوق ما قالته الأسرة أوّل مرة تُضيع إجابة حقيقية |
| `400 VALIDATION` | نوع طلب لا يقبله المركز (ومعه قائمة المقبول) · `RESCHEDULE` بلا موعد · تاريخ غير `YYYY-MM-DD` |
| `403 FORBIDDEN` | يقرأ الطفل ولا يتصرّف نيابةً عن الأسرة |

`log_date` **يوم تقويمي**، وحذفه يعني «اليوم» بحساب الداتابيز لا بساعة الخادم.
وأنواع الطلبات **صفوف بحث**، لا ثوابت في Go — فالرفض يستطيع أن يقول ما الذي يقبله
هذا المركز فعلًا.

# الفواتير — قراءة فقط

**البوابة لا تستلم مالًا.** لا نقطة دفع هنا، ولن تكون قبل قرار مستقلّ.

| النقطة | ترجع |
|---|---|
| `GET /api/v1/children/{child_id}/invoices` | الفواتير |
| `GET /api/v1/invoices/{invoice_id}` | فاتورة ببنودها ودفعاتها |
| `GET /api/v1/children/{child_id}/packages` | الباقات، ومعها `sessions_left` |
| `GET /api/v1/children/{child_id}/balance` | المستحقّ |

**وسلّم ثالث، من نفس عائلة سلّمَي الملاحظة والتقرير:** ولي أمر بلا `BILLING.VIEW`
يصل فقط إلى فاتورة **غادرت `DRAFT`**. فاتورة قيد التجهيز ليست فاتورة، ووضعها أمام
الأسرة هو مطالبتها بمبلغ ما زال يتحرّك. ومسودّة عن طفلها هي تُجيب `404`.

**المبالغ نصوص عشرية دقيقة، لا أرقام عائمة** — `"total_amt": "4000.00"`. راجع D-25:
المال يُجمع ويُقارن بدفعة، و`0.1 + 0.2` ليست `0.3` في الفاصلة العائمة. والعملة تأتي
مع المبلغ من صفّ المركز.

**ولا يخرج:** `reference` على الدفعة — مرجع تحويل أو بطاقة يحفظه المركز للتسوية، وهو
بالضبط نوع الحقل الذي يتبيّن أنه يحوي جزءًا من رقم بطاقة. ولا `note_ar` ولا `einv_ref`
ولا `einv_status`: دفاتر المركز مع مصلحة الضرائب ليست جزءًا مما دُفع.

# البث المباشر

**بثّ فقط — ولا تسجيل، أبدًا.** لا شيء هنا يكتب بايت وسائط في أي مكان.

| النقطة | ماذا تفعل |
|---|---|
| `POST /api/v1/sessions/{session_id}/stream` | يفتح نافذة مشاهدة |
| `GET /api/v1/stream/media` | **الوسائط**، عبر الـ API |
| `POST /api/v1/stream/close` | يُنهي النافذة فورًا |

## ما **لا** يحتويه الرد — وهو التصميم كلّه

```json
{ "playback_path": "/api/v1/stream/media", "expires_at": "…", "expires_in_seconds": 900 }
```

**ولا توكن. ولا مسار كاميرا. ولا معرّف كاميرا. ولا عنوان بوابة.**

التوكن يسافر في **كوكي `HttpOnly`** مقصورة على مسار التشغيل، `SameSite=Strict` —
فلا سكربت يقرؤها، ولا موقع آخر يستطيع تضمين البثّ. و`playback_path` ثابت واحد لكل
مشاهد ولكل جلسة، فلا يدلّ على شيء. التفاصيل والبدائل المرفوضة في **D-24**.

`GET /api/v1/stream/media` هي **النقطة الوحيدة** غير المصادَقة بـ Bearer، والسبب ملموس:
عنصر `<video>` لا يستطيع ضبط ترويسة `Authorization`. والكوكي بديل **أضيق** لا أوسع —
جلسة واحدة، كاميرا واحدة، مستخدم واحد، ربع ساعة سقفًا، وقابلة للإلغاء في اللحظة.

## البوّابة

| الحالة | متى |
|---|---|
| `201` | مسموح — والكوكي مضبوطة |
| `403 FORBIDDEN` | يرى الجلسة ولا يملك `can_view_live_flg` على صلة القرابة |
| `404 NOT_FOUND` | ليست جلسة طفله — **`404` لا `403`**، فـ`403` كانت ستؤكّد وجودها |
| `409 NOT_LIVE` | الجلسة ليست جارية الآن |
| **`503 STREAM_UNAVAILABLE`** | **لا بوّابة وسائط، أو بوّابة لا يجوز أن تخدم أسرة** |

**و`503` هي إجابة التركيب الجديد افتراضيًا.** `MEDIA_GATEWAY_BASE_URL` فارغ
و`MEDIA_GATEWAY_IS_TEMPORARY` يساوي `true` في السكيما — فلا يُصدَر توكن حتى يضبط
إنسانٌ نفقًا مُسمّى على نطاق يملكه المركز ويُطفئ العلم يدويًا. ونفق `trycloudflare`
مرفوض بالاسم. راجع D-19.

**السقف ربع ساعة** مطبَّق في دالة الإصدار **وفي قيد `CHECK` على الصفّ**، فلا بارامتر
ولا نداء يستطيع توسيعه.

**وكل مشاهدة تترك أثرًا** في `stream_views` وفي سجلّ التدقيق — وهذا هو الشيء الوحيد
الذي وُجد ذلك الجدول لمنعه: أن يشاهد أحدٌ طفلًا في جلسة علاجية بلا أثر.

# تطبيق المركز — الإنشاء والتعديل والأرشفة

منذ **D-26** صار PostgreSQL مصدر الحقيقة، وفُتحت الكتابة بالهجرة `0012`. قبلها كانت
السكيما **للقراءة بحكم البناء**: ٤١ سياسة `SELECT` وصفر منح كتابة.

## الدخول — بابان لا يتقاطعان

| | |
|---|---|
| **الأسرة** | `POST /api/v1/auth/otp/request` ثم `…/verify` — تثبت هاتفًا |
| **الموظّف** | `POST /api/v1/auth/staff/login` `{username, password}` — يثبت كلمة مرور |

الرد واحد: `{token_type, token, expires_at}`. و`hbh.verify_password` **ترفض ولي أمر
من باب الموظّفين** — وكل فشل يجيب `401 UNAUTHENTICATED` بنفس الرمز: أن يُقال لغريب
«هذا الحساب يدخل بطريقة أخرى» هو أن يُقال له إن الحساب موجود.

## أربعة عشر موردًا، خمسة أفعال

`services · rooms · cameras · activity-library · service-packages · therapists ·
working-hours · caseload · children · guardians · plans · goals · child-activities ·
measurements`

| | |
|---|---|
| `GET /api/v1/<name>` · `GET …/{id}` | قراءة (`children` تُقرأ من مسارات البوابة) |
| `POST /api/v1/<name>` | `201` والصفّ كاملًا |
| `PATCH /api/v1/<name>/{id}` | `200` والصفّ بعد التعديل |
| **`DELETE /api/v1/<name>/{id}`** | **أرشفة** — `204` |
| `POST /api/v1/<name>/{id}/restore` | تراجع — `204` |
| `GET /api/v1/<name>?archived=true` | يشمل المؤرشف — لحامل صلاحية الإدارة وحده |

**و`DELETE` ليست حذفًا.** لا توجد منحة `DELETE` على **أي** جدول في هذه السكيما، فالحذف
الصلب ليس ممنوعًا بل **مستحيل** من هذا الاتصال. الفعل يضبط `active_flg = false` ويختم
الوقت، فالصفّ قابل للاسترجاع ووجوده السابق يبقى مرئيًا لمدقّق. وبيانات الطفل السريرية
لا تُحذف فعليًا دون إجراء امتثال موثَّق — والقاعدة نجت من انتقال المحرّك.

## ثلاثة أشياء لا يرسلها العميل

| الحقل | لماذا |
|---|---|
| `center_id` | يُشتقّ من المتصل (D-3). عميل يسمّي المركز يكتب طفلًا في مركز آخر |
| `active_flg` | الأرشفة لها مسارها، وضبط العلم مباشرةً يتخطّى الختم الذي يجعلها قابلة للتدقيق |
| `status` على `plans` | آلة حالة بمشغّل انتقال — القاعدة ٥ |

وإرسال أيٍّ منها يرجع **`400`** باسم الحقل، لا تجاهلًا صامتًا: التجاهل يجعل المتصل
يظنّ أن ما أرسله طُبِّق.

## الصلاحية تقرّر، لا المسمّى الوظيفي

| | يستطيع | لا يستطيع |
|---|---|---|
| **استقبال** | تسجيل طفل وتعديله (`CHILD.CREATE` · `CHILD.EDIT`) | إنشاء خدمة أو كاميرا |
| **مدير المركز** | الكتالوج والطاقم والكاميرات | — |
| **ولي أمر** | لا شيء من هذا | — |

**والفحص داخل السياسة لا في Go.** ليس في `crud_handlers.go` فحص صلاحية واحد؛ المحرّك
يرفض، والطبقة تترجم الرفض. شرط في المعالِج كان سيصير نسخة ثانية من قاعدة.

**والكاميرا تحتاج صلاحيتين معًا** — `CATALOG.MANAGE` **و** `LIVE.VIEW`. مَن يحرّر قائمة
الأسعار لا يوجّه بذلك كاميرا إلى غرفة أخرى. و`gateway_path` و`credential_ref` **تُكتبان
ولا تُقرآن أبدًا** — محذوفتان من كل رد وكل قائمة وكل رسالة خطأ.

## رموز الرفض في الكتابة

| الحالة | الرمز | متى |
|---|---|---|
| `403` | `FORBIDDEN` | يقرأ الشيء ولا يكتبه — **بعد أن ثبت أنه يقرأه** |
| `404` | `NOT_FOUND` | ليس صفّه، أو غير موجود |
| `400` | `VALIDATION` | ومعه `fields.field` أو `fields.constraint` |

و`fields.constraint` قيمه: `DUPLICATE` · `REQUIRED` · `NO_SUCH_REFERENCE` · `FORMAT` ·
`REFUSED`. **ولا يُذكر اسم القيد** — «يوجد واحد بهذا الكود» قابل للتصرّف،
و`uq_services_code` كشفٌ للسكيما.

# يوم المركز — القراءة المفهرسة بالمركز

كل ما سبق مقيَّد **بطفل**، وهو الشكل الصحيح لولي الأمر: يدخل من طفله. وموظّف
الاستقبال يدخل من **يوم**. تجميع الثاني من الأول يعني نداءً لكل طفل ودمجًا في
المتصفّح — يكسر الترتيب والترقيم، ولا يعرف عن طفل لم يُنادَ عليه.

| النقطة | المرشِّحات |
|---|---|
| `GET /api/v1/appointments` | `date` · `from`/`to` · `therapist_id` · `room_id` · `status` · `page` · `limit` |
| `GET /api/v1/sessions` | `date` · `therapist_id` · `status` · `page` |
| `GET /api/v1/reports` | `status` · `from`/`to` · `child_id` · `page` |
| `GET /api/v1/invoices` | `status` · `from`/`to` · `child_id` · `page` |
| `GET /api/v1/requests` | `status` · `kind` · `page` |

**مسار واحد لجمهورين.** ولي الأمر يسأل نفس النقطة فيرى صفوف طفله؛ والموظّف يرى صفوف
المركز. **السياسة** تقرّر، ولا يوجد مسار ثانٍ لتطبيق المركز.

**وكل صفّ يحمل الأسماء لا المعرّفات وحدها** — اسم الطفل والأخصائي والغرفة والخدمة. صفٌّ
يحمل `therapist_id` وحده يجبر الشاشة على نداء لكل سطر، وهو نفس العيب في علبة أصغر.

**واليوم يُحسَب بتوقيت المركز** من صفّ المركز، لا بـ UTC ولا بثابت في الكود. الافتراضي
بلا `date` هو اليوم، والنافذة **نصف مفتوحة** — فموعد يبدأ منتصف الليل ينتمي ليوم واحد
لا ليومين.

## الفتحات المتاحة

| النقطة | المرشِّحات |
|---|---|
| `GET /api/v1/appointments/slots` | `therapist_id` · `service_id` · `date` · `room_id` (اختياري) |

يجيب عن **السؤال المعكوس**: لا «هل هذا الوقت مقبول؟» بل «أي الأوقات مقبولة؟». كانت
الشاشة تملك الأول وحده، فإيجاد فجوة في يوم مزدحم يعني اقتراح وقت بعد وقت حتى يمرّ أحدها.

**والقواعد ليست هنا.** `hbh.available_slots` يولّد المرشّحات من ساعات عمل الأخصائي
ومدّة الخدمة، ثم يمرّر **كل مرشّح** على `hbh.validate_slot` — الدالة نفسها التي يمرّ
بها الحجز. نسخة ثانية من «متى تجوز الجلسة» كانت ستتّفق مع الأولى إلى أن يغيّر أحدهم
واحدة منهما، فتعرض الشاشة فتحة يرفضها الحجز.

**ولا يسأل عن الطفل.** الطفل يُختار بعد الفتحة، فـ`CHILD_BUSY` يُجاب عند التأكيد من
`validate_slot` نفسها. «متاح» هنا تعني: الأخصائي وغرفةٌ ما متاحان.

**وكل فتحة تحمل غرفة واحدة** — أول غرفة خالية — لا نفس الساعة مكرّرة بعدد الغرف.

ويحتاج `APPOINTMENT.BOOK`. الدالة `SECURITY DEFINER`، فتفحص الصلاحية بنفسها **وترفع**
`HB240` (‏403) بدل أن ترجّع صفر صفوف: «لا يجوز لك السؤال» و«لا توجد فتحة» جوابان
مختلفان، وشاشة تطبع الثاني مكان الأول ترسل الاستقبال ليتّصل بأسرة عن يوم لم يمتلئ أصلًا.

# الكتابة التشغيلية

| النقطة | فوق |
|---|---|
| `POST /api/v1/appointments/validate` | `validate_slot` |
| `POST /api/v1/appointments` | `book_appointment` |
| `PATCH /api/v1/appointments/{id}/status` | آلة حالة الموعد |
| `POST /api/v1/appointments/{id}/session` | `start_session` |
| `PATCH /api/v1/sessions/{id}/close` | `close_session` |
| `PUT /api/v1/sessions/{id}/note` | `write_session_note` |
| `POST /api/v1/reports` | `create_report` — يفتح مسودّة. يحتاج `REPORT.WRITE` ووصولًا للطفل. المركز والفرع ورقم التقرير والكاتب والحالة تُشتق في الخادم ولا تُقبل من العميل |
| `PATCH /api/v1/reports/{id}` | `update_report` — تعديل مسودّة فقط. تقرير منشور يُرفض بـ`HB033` |
| `POST /api/v1/reports/{id}/publish` | `publish_report` — يحتاج `REPORT.PUBLISH` ووصولًا للطفل، ويرفض تقريرًا بلا ملخّص |

| `POST /api/v1/invoices/{id}/payments` | إدراج دفعة |
| `POST /api/v1/children/{id}/packages` | `sell_package` |
| `PATCH /api/v1/requests/{id}` | `decide_request` |

**`validate` قبل `book` هي الفرق بين شاشة تُستعمل وشاشة تُكره.** الموظّفة تعرف أن
الأخصائي مشغول **وهي تختار**، لا بعد ملء النموذج. ورفض التحقّق **`200` وفيه
`ok:false`** لا حالة خطأ: سؤال طُرح وأُجيب، ولم يفشل شيء.

**الحالة إلى نفسها لا تُرفَض** — المشغّل لا يُستشار إلا حين تتغيّر الحالة فعلًا، فـ`PATCH`
يصير مُتكرِّرًا بأمان لشاشة قد تعيد المحاولة. والانتقال **غير الشرعي** يُرفَض `409`.

## رموز الرفض التشغيلية

| الرمز | الحالة | من |
|---|---|---|
| `SLOT_UNAVAILABLE` · `SLOT_TAKEN` | `409` | فتحة مرفوضة أو محجوزة |
| `ILLEGAL_TRANSITION` | `409` | آلة حالة |
| `NOT_CHECKED_IN` · `SESSION_EXISTS` · `NO_CASELOAD` | `409` | شروط بدء الجلسة |
| `ALREADY_PUBLISHED` · `OVERPAYMENT` | `409` | نشر مكرّر · دفعة تتجاوز المستحق |
| `FORBIDDEN` | `403` | يقرأ ولا يكتب |
| `REFUSED` | `409` | رفض من قاعدة لا تُميَّز بالرمز — انظر أدناه |

> **`HB052` غامض في السكيما:** يُستعمل لـ«يحتاج `BILLING.MANAGE`» **و**لـ«الفاتورة لم تعد
> تقبل التغيير». لا يمكن التمييز بينهما من الرمز، فالخريطة تختار `409 REFUSED` — الأقلّ
> ادّعاءً: لا تؤكّد مشكلة صلاحية قد لا تكون موجودة.

# تأليف الفاتورة — وما يربط الأخصائي بخدمته

نقصان اكتشفتهما جلسة الواجهة **بمحاولة تشغيل مركز كامل عبر هذه الواجهة**، لا بمراجعة.
كلاهما يجعل مركزًا جديدًا عاجزًا عن العمل رغم أن كل شيء آخر موجود.

## ١. لم يكن هناك ما يُنشئ فاتورة

`issue` و`payments` يعملان على فاتورة **موجودة**، و`sell_package` لا تصنع واحدة —
فشاشة الفواتير كان فيها فعلان بلا طريق يصل إليهما.

| النقطة | |
|---|---|
| `POST /api/v1/invoices` | `{child_id, guardian_id?, due_date?, note_ar?}` ← `201 {invoice_id}` |
| `POST /api/v1/invoices/{id}/lines` | `{description_ar, qty, unit_amt, service_id?}` ← `201 {line_id}` |
| `DELETE /api/v1/invoices/{id}/lines/{line_id}` | `204` — أرشفة، لا حذف |

**ما لا يُرسله المتصل هو بيت القصيد.** الرقم من سلسلة `hbh.next_number`، والعملة من صفّ
المركز، ونسبة الضريبة من `hbh.param` **وتُثبَّت على الفاتورة لحظة الإنشاء** — فتغيّر النسبة
الشهر القادم لا يعيد صياغة فاتورة صدرت قبله. والمجاميع **تُحسَب** (D-17): `line_amt`
مشتقّ من `qty × unit_amt`، ومتصل يرسل الثلاثة قد يرسل أرقامًا لا يسندها حساب.

والمبالغ **نصوص عشرية داخلة وخارجة** (D-25). رقم JSON للمال هو float، وأقرب float إلى
`10.10` ليس `10.10` — وهو شيء غريب أن تكتشفه على فاتورة.

**بعد `issue` لا تتحرّك الأرقام**: إضافة سطر أو حذفه تُرفَض بـ`409 ILLEGAL_TRANSITION`
(`HB050`). الأسرة أُعطيت رقمًا لتدفعه.

**رمز جديد `HB054`** — الطفل ليس ممّن يملك المتصل التصرّف عنهم، فيرجع `403`. كُتب رمزًا
مستقلًا **لأن `HB052` محمَّل أصلًا** بمعنيين؛ إضافة ثالث تُفقد الواجهة آخر ما تستطيع قوله
بدقّة.

## ٢. لم يكن هناك ما يربط أخصائيًا بخدمة

`validate_slot` تُجيب `THERAPIST_SERVICE_MISMATCH` إن لم يوجد صفّ في
`hbh.therapist_services` — ولم تكن هناك نقطة تكتب فيه. فمركز يُنشئ أخصائييه وخدماته
وغرفه وأطفاله **ولا يحجز موعدًا واحدًا**.

```
GET    /api/v1/therapists/{therapist_id}/services
POST   /api/v1/therapists/{therapist_id}/services   {service_id}
DELETE /api/v1/therapists/{therapist_id}/services/{service_id}
GET    /api/v1/services/{service_id}/therapists
GET    /api/v1/service-therapists
```

**والأخيرة هي نفس الزوج مقروءًا من الجهة الأخرى**، وهي الجهة التي تحتاجها شاشة الحجز:
قائمة تعرض **كل** الأخصائيين تسمح باختيار من لا يقدّم الخدمة، ثم تجيب `validate_slot`
بـ`THERAPIST_SERVICE_MISMATCH` عن حقيقة كانت معروفة قبل الاختيار.

**والأخيرة الرابعة ترجّع كل الأزواج القابلة للتنفيذ دفعةً واحدة**، ومعها اسم الخدمة واسم الأخصائي ومدّة الخدمة. شاشة الحجز تعرضهما **اختيارًا واحدًا** بدل سؤالين، فالتركيبة غير المتوافقة لا تصير «غير مستحسَنة» بل **غير قابلة للتعبير عنها**. والسؤال لكل خدمة على حدة كان سيصير طلبًا لكل صفّ في القائمة، وتصل إجاباته بالترتيب الذي تختاره الشبكة.

**وترجّع النشِطين وحدهم** — `active_flg` و`status = 'ACTIVE'` — لا ترتيبًا للبيت:
`validate_slot` ترفض غير النشِط بـ`THERAPIST_UNAVAILABLE`، وعرضه هنا كان ينقل نفس
العيب اسمًا واحدًا إلى اليسار.

**ليس ضمن الأربعة عشر موردًا** لسبب آليّ لا اجتهادي: الجدول مفتاحه **الزوج**
(`therapist_id`, `service_id`) بلا معرّف بديل، فلا يمكن مخاطبته بشكل `/{id}` الذي
تتشاركه بقيّة الموارد. وإقحامه فيه كان يعني إضافة عمود للسكيما إرضاءً لعُرف توجيه.

**ويسهل الخلط بينه وبين `caseload` وهما سؤالان مختلفان:** `caseload` أخصائي↔**طفل**
ويجيب «هل يجوز لهذا الشخص أن يدير هذه الجلسة»، وهذا أخصائي↔**خدمة** ويجيب «هل يمارس
التخاطب أصلًا». كلاهما مطلوب ولا يُغني عن الآخر.

**والربط يُعاد تفعيله لا يُرفَض كمكرّر**: سحب خدمة من أخصائي ثم إعادتها أمر عادي، والبديل —
تصادم على مفتاح فريد مع صفّ **لا يراه المتصل** — طريق مسدود على الشاشة.

## ٣. تصحيح: `guardian` على صفّ الطلب

كان معلَّقًا على `user_id`، فوليّ أمر **بلا حساب** — أسرة ملأت نموذجًا ورقيًا، أو أسرة
حوّلها `convert_enrolment` — يصل طلبها **بلا وليّ أمر إطلاقًا**. فيرى الاستقبال الطلب ولا
يرى **مَن طلبه**، وهو الشيء الوحيد الذي وُجدت الشاشة لتجيب عنه.

صار `GuardianRef` معلّقًا على `guardian_id`: `{guardian_id, full_name_ar, mobile, user_id?}`.
و`user_id` اختياري لأن الشاشة تحتاج أن تعرف **هل ثمّة حساب** لتفتحه.

# الالتحاق · الاستبيان · سجلّ التشغيل

## طلب الالتحاق — المسار الوحيد بلا مصادقة

```
POST  /api/v1/enrolments        ← بلا توكن
GET   /api/v1/enrolments        ?status&page&limit&archived
GET   /api/v1/enrolments/{id}
PATCH /api/v1/enrolments/{id}   {status, note_ar?}
POST  /api/v1/enrolments/{id}/convert   ← 201 {guardian_id, child_id, child_no}
```

كل نقطة أخرى في هذه الخدمة ترفض متصلًا بلا توكن؛ هذه تجيبه. وأمانها ليس في أنها مفتوحة
قليلًا، بل في **أنها تصل إلى دالة واحدة `SECURITY DEFINER` تقرّر بنفسها**، والمعاملة التي
تجري فيها **لا تحمل هوية** — فلا شيء آخر في السكيما مرئيّ لها.

**والسبب لا يسافر.** قاعدة البيانات تُجيب بـ`REJECTED` أو `TOO_MANY_FOR_MOBILE` أو
`TOO_MANY_FOR_IP`، ولا واحد منها يصل للمتصفّح كما هو:

- `REJECTED` تعني «كود مركز مجهول» — وتمريرها تُمكّن أي أحد من **إحصاء المراكز** بتجربة الأكواد.
- الحدّان يُفرَّق بينهما **في السجلّ لا في الجواب**. قول «تجاوزت الحدّ لهذا الجوّال» يُخبر
  غريبًا أن الرقم الذي كتبه **معروف لهذا المركز** — وهذه حقيقة عن أسرة.

فالرفض شكلان: `429` لحدّ و`400` لغيره، بلا تفصيل على أيّهما. والتفريق يُسجَّل في
`audit_log` حيث يراه المركز.

**والقراءة مقفولة تمامًا**: مجهول الهوية يقرأ **صفر صفوف** من `enrolment_applications` ولا
يستطيع الإدراج مباشرة (`42501`).

**الحالات:** `NEW → CONTACTED → ASSESSMENT_BOOKED → ENROLLED` · و`REJECTED`/`DUPLICATE`.
غير الشرعي `409 ILLEGAL_TRANSITION` (`HB090`/`HB091`)، وبلا `ENROLMENT.MANAGE` يرجع `403`
(`HB092`).

**والتحويل لا يمنح مشاهدة الطفل** — مشاهدة طفل في جلسة علاجية تحتاج موافقة مسجَّلة (D-24)،
وملء نموذج ليس موافقة. أخطر مفتاح في هذا النظام لا يُشعله موظّف استقبال بضغطة.

**و«وقت التواصل» يُختم من آلة الحالة لا من الـ API** (الهجرة 0026). كان الطابور يعرض أسرة
«تم التواصل معها» بلا تاريخ — أسوأ من عمود غائب، لأنه يُقرأ «كلّمناهم، في وقت غير محدّد».
ووقتُ الانتقال جزء من الانتقال، لا حقل يرسله متصل.

## استبيان الرضا

```
GET  /api/v1/nps/due                    ← {"survey": {...}} أو {"survey": null}
POST /api/v1/nps/{survey_id}/response   {score, comment_ar?, context_kind?, context_id?}
POST /api/v1/nps/{survey_id}/skip
GET  /api/v1/nps/summary
```

`null` **جواب عادي لا 404**: «لا شيء نسألك عنه» هو الحالة الغالبة، وشاشة تعدّها خطأً
تسجّل فشلًا مع كل تحميل صفحة.

**و`skip` ليست ترفًا.** المهلة تبدأ حين يُسجَّل **شيء**، ونافذة أُغلقت لا تسجّل شيئًا —
فعميل يعرض السؤال ويهمل الإغلاق يحوّل سؤالًا واحدًا إلى سؤال في كل صفحة.

**ونصّ السؤال من قاعدة البيانات لا من الواجهة**، وهذا ليس استثناءً من D-11: رمز الخطأ
مفردات ثابتة تترجمها الواجهة، والسؤال **محتوى يكتبه المركز ويغيّره بلا إصدار**. سؤال
مكتوب في Angular لا يستطيع تغييره من يملك السؤال.

والإعداد **موردٌ في جدول CRUD** باسم `nps-surveys` — يحتاج `NPS.MANAGE`. واستبيان لا شرط
إطلاق له مرفوض بقيد (`23514`) لا يقبع صامتًا بلا إطلاق.

**ولوحة النتائج تعرض `nps` لا `mean_score`** — رقمان مختلفان يشبهان بعضهما: في تشغيلة
القبول `nps = 25` بينما المتوسّط `7.25`.

## سجلّ التشغيل

وسيط واحد يكتب صفًّا لكل طلب انتهى، **وثلاثة عروض تقرؤه** (تحتاج `OPS.VIEW`):

```
GET /api/v1/ops/health    ← لكل route+method: calls · p50 · p95 · max · error_pct
GET /api/v1/ops/errors    ← آخر الأخطاء بالرمز والتفصيل
GET /api/v1/ops/activity  ← من دخل، كم طلبًا، وآخر ظهور
```

خمس خصائص مؤكَّدة بفحوص:

1. **`route` قالب لا مسار.** `/api/v1/children/{child_id}` لا `/api/v1/children/42`.
   والقالب يأتي من **ثابت الموجِّه نفسه** لا من الطلب — وطلب لم يطابق مسارًا يُسجَّل تحت
   `(unrouted)`، لأن مسار الـ404 يختاره من أرسله: تسجيله حرفيًا يُتيح لغريب كتابة ألف صفّ
   متمايز في شاشة مشغّل.
2. **كل رد ≥ ٤٠٠ يحمل رمزًا.** يُختَم في `writeErrorFields` — المكان الوحيد الذي يغادر منه
   رفضٌ هذه الخدمة — فلا يستطيع معالِج أن ينساه.
3. **`error_message` فارغة دائمًا.** هذه الخدمة تُجيب برموز لا بجُمل، والنصّ الوحيد المتاح
   لوضعه هناك هو خطأ قاعدة بيانات **قد يقتبس قيمة صفّ** — واسم طفل في سلسلة خطأ يضع بيانات
   سريرية على شاشة تشغيل.
4. **`detail` يسمّي الحقل لا القيمة.** `{"field":"limit"}` — ولهذا يجوز إبقاؤه.
5. **الهوية تُقرأ من الطلب.** مجهول يُسجَّل بـ`user_id = NULL`، وهذا مقصود ومُختبَر.

**لا يُسجَّل `/healthz` ولا `/readyz`**: منسّق يناديهما كل ثوانٍ إلى الأبد، ودفن المرور
الحقيقي تحتهما يُفقد الشاشة معناها ويُكبّر الجدول.

**ولا يُفشِل الوسيط طلبًا أبدًا.** الدالة تبتلع أخطاءها، وهذه الطبقة تبتلع ما قد يقع قبل
الوصول إليها — فطلب **نجح** لا يصير طلبًا فشل لأن سطر سجلّ تعذّرت كتابته.

`REQUEST_LOG=false` يُطفئه. المفتاح موجود لأنه يكلّف رحلة إلى قاعدة البيانات لكل طلب:
مشغّل يراقب خدمة تحت حِمل لا بدّ أن يستطيع إطفاء ما يقيسها. وليس مفتاح خصوصية — الصفّ
يحمل قالب مسار وحالة ومدّة، لا جسمًا ولا سلسلة استعلام.

# الإعدادات — صفّ المركز وبارامتراته

شاشة الإعدادات كانت تقول في لافتة إنها للقراءة فقط، لأن ذلك كان صحيحًا: لا نقطة
تقرأ `hbh.sys_params` ولا تكتب صفّ `hbh.centers`. والصلاحية `SETTINGS.MANAGE`
موجودة في البذرة منذ البداية، يملكها `CENTER_ADMIN` وحده، **ولم يكن أحد يفحصها**.

## البارامتر صفّ — والتعديل نسخة للمركز

| النقطة | ماذا |
|---|---|
| `GET /api/v1/settings/params` | كل بارامتر بقيمته الفعّالة · `{ code, value, dataType, descriptionAr, editable, overridden, defaultValue }` |
| `PATCH /api/v1/settings/params/{code}` | `{"value": "..."}` → `200 { code, value }` |
| `DELETE /api/v1/settings/params/{code}` | أعده للافتراضي → `200 { code, value }` — والقيمة هي الافتراضية التي صارت سارية |

القيمة الفعّالة تُحلّ **نسخة المركز قبل العامّة**، تمامًا كما تفعل `hbh.param()`،
و`overridden` يقول أيّ الاثنتين أجابت. والكتابة **لا تمسّ الصفّ العامّ أبدًا**: تُنشئ
أو تُحدّث صفًّا بـ`center_id` بجواره. فالقيمة المشحونة تبقى موجودة دائمًا، و«أرجعها
كما كانت» زرّ واحد لا تذكُّر رقم.

**وليس كل بارامتر إعدادًا.** `hbh.sys_params.editable_flg` يقرّر، **وافتراضيه
`false`**: بارامتر يُضاف غدًا مقفول حتى يفتحه أحد بقصد. والمقفولة اليوم مقفولة
بأسباب مكتوبة في البذرة نفسها — `RECORDING_ENABLED` («التسجيل ممنوع دائمًا … ولا
تُغيَّر») و`STREAM_TOKEN_TTL_MIN` («لا تزيد أبدًا») وحدود الأمان ومنع الإساءة
وصيغتا الجوّال والرقم القومي.

كل ذلك في `hbh.set_center_param(code, value)` — `SECURITY DEFINER`، تفحص الصلاحية
والعلامة والنوع. **ولا منحة كتابة على الجدول**: `hbh_app` يملك `SELECT` فقط،
والدالة هي الباب الوحيد.

**و«الحذف» ليس حذفًا.** القاعدة ٣: الحذف ناعم دائمًا، ولا منحة `DELETE` على أي
جدول — ولم تتغيّر هنا. صفّ النسخة **يُعطَّل** (`active_flg = false` مع
`deleted_at`)، و`hbh.param()` تقرأ `AND active_flg` فتتخطّاه إلى الصفّ العامّ.
والصفّ باقٍ بقيمته: «مَن وضع المركز على ٢١ يومًا في مارس» سؤال يُجاب.

ولأن `uq_sys_params` ليس جزئيًّا، الصفّ المعطَّل يحتفظ بمكانه — و`ON CONFLICT`
في `set_center_param` يعيده للحياة (`active_flg = true, deleted_at = NULL`)
بدل أن يصطدم به. فتعديل بارامتر سبق إرجاعه للافتراضي يحيي نفس الصفّ.

**ولا ترفع حين لا شيء لتصفيره.** طلب الافتراضي وهو ساري بالفعل ليس خطأً — هو
شاشة رُسمت قبل لحظة. الردّ هو القيمة السارية في الحالتين.

## صفّ المركز

| النقطة | ماذا |
|---|---|
| `PATCH /api/v1/settings/center` | جزئي — `name_ar` · `country_code` · `currency_code` · `time_zone` · `weekend_days` → `204` |
| `GET /api/v1/settings/time-zones` | قائمة المنتقي — `{ name, offsetMinutes }` · ٥١٩ منطقة |

الحقول **اختيارية كلّها**، وما لا يُرسَل لا يُلمس: الجسم `{"time_zone": "..."}` لا
يُفرّغ اسم المركز. `code` ليس منها — لا منحة له والمشغّل يرفضه — وكذلك `name_en`:
`GET /me` لا يردّه، وحقل يُكتب ولا يُقرأ ليس حقلًا قابلًا للتعديل.

**والمنطقة الزمنية تُختار من قائمة، لا تُكتب.** المصدر `pg_timezone_names` —
وهو نفسه ما يفحص عليه المشغّل في 0059، فالقائمة لا تعرض اسمًا سترفضه القاعدة.
وتُصفّى في Go عبر `time.LoadLocation`: القيمة تُحمَّل بالاسم لحساب «اليوم»، ومنطقة
يعرفها المحرّك ولا يقدر يحمّلها هذا البناء كانت ستعبر المشغّل ثم تُسقط شاشة
المواعيد. هذا ليس نسخة ثانية من القاعدة — المشغّل يقرّر ما يُخزَّن، وهذه تجيب
على سؤال أضيق: ما الآمن أن يُعرَض.

و`posix/` و`right/` و`Etc/` مستبعدة — أسماء مكرّرة ومقابلات ثابتة، وأربعة أسماء
لمنطقة واحدة تجعل القائمة أصعب لا أكمل. و`UTC` باقية: جواب حقيقي لمركز لا يريد
توقيتًا محلّيًا.

**الثلاث بوّابات في القاعدة لا في هذه الطبقة** (الهجرة 0051): منحة على مستوى
الأعمدة تقرّر أيّ عمود يتحرّك أصلًا · وسياسة RLS تطلب `SETTINGS.MANAGE` من داخلها ·
ومشغّل `BEFORE` يحكم على التغيير نفسه. فمن لا يملك الصلاحية **لا يُرفض برسالة**:
السياسة لا تطابق صفًّا، والتحديث يعدّ صفر صفوف — و`404` هو الجواب، كما في كل مكان
آخر هنا.

## رموز الرفض

| الرمز | الحالة | من |
|---|---|---|
| `HB160` | `409 IMMUTABLE` | كود المركز ثابت — البذور ومُصدِّر الموقع يطابقون عليه |
| `HB161` | `409 CURRENCY_LOCKED` | العملة بعد وجود فواتير أو مدفوعات — لا شيء يحوّل المبالغ المخزَّنة |

| `HB171` | `400 VALIDATION` ومعه `fields.field = national_id` | رقم قومي بطول غير `NATIONAL_ID_LENGTH` |

**ولماذا `HB162` يسمّي حقله.** القيمة تُحمَّل بالاسم في

يُسقط تلك الشاشات بـ`500` — والعطل يظهر شاشتين بعيدًا عن الصندوق الذي كتبه.

## `22001` — وكانت `500`

`centers.country_code` من نوع `character(2)`، فـ`EGY` يرفضه **النوع** بـ`22001`
قبل أن يصل إلى قيد `CHECK` أصلًا — بلا اسم قيد. ولم يكن الرمز مُصنَّفًا، فكان يسقط
إلى `500`. أُضيف إلى عائلة «ما لا تقبله السكيما» بجوار `22P02` و`22007` و`22003`،
**وأثره يتعدّى هذه النقطة**: أي قيمة أطول من عمودها في أي مورد CRUD كانت تُبلَّغ
عطلًا في الخادم وصارت `400`.

# ملفّ الأخصائي

**خلف تسجيل الدخول دائمًا** — قرار المالك. لا قراءة بلا مصادقة تدخل السكيما، ويبقى
الالتحاق المسار الوحيد من نوعه.

```
PATCH  /api/v1/therapists/{therapist_id}/profile      {bio_ar?, practice_since_year?, age_from_mon?, age_to_mon?, clear?[]}
GET    /api/v1/therapists/{therapist_id}/languages
PUT    /api/v1/therapists/{therapist_id}/languages    {lang_code, level_code?, is_native?, runs_sessions?}
DELETE /api/v1/therapists/{therapist_id}/languages/{lang_code}
GET    /api/v1/therapists/{therapist_id}/certificates
POST   /api/v1/therapists/{therapist_id}/certificates {title_ar, issuer_ar?, year_awarded?, expires_on?, attachment_id?, registration_no?}
PATCH  /api/v1/certificates/{certificate_id}/image    {is_image_public}
POST   /api/v1/therapists/{therapist_id}/consent      {text_version?}
DELETE /api/v1/therapists/{therapist_id}/consent
POST   /api/v1/therapists/{therapist_id}/publish
```

**النبذة لها نقطتها الخاصة ولا تمرّ بالمورد العام.** وُضعت هناك أوّلًا فلم يستطع الأخصائي
تحرير نبذته هو: السياسة على `hbh.therapists` تطلب `STAFF.MANAGE`. وتوسيعها كان يمنحه
`status` و`user_id` و`branch_id` معها — **لأن RLS تمنح صفوفًا لا أعمدة**.

**«غير مذكور» و«فرّغه» طلبان مختلفان.** كل حقل مؤشّر؛ التفريغ يُقال صراحةً بـ
`{"clear":["age_from_mon"]}`، واسم خارج الملفّ في `clear` يأخذ `400`. شاشة تحرّر النبذة
لا تمسح مدى عمر لم تعرضه.

**والنشر يحتاج موافقة الأخصائي مسجَّلة** — مَن ومتى وأي نصّ وافق عليه. رمزها
`409 CONSENT_REQUIRED` لا `403`: المتصل غالبًا **يملك** الصلاحية، والناقص شيء يُذهب
ويُؤخذ. و`403 NOT_YOUR_CONSENT` لمن يحاول الموافقة نيابةً عن غيره — **والمدير يملك كل
صلاحية في السكيما ويأخذه**.

**وسحب الموافقة يُنزل الصفحة معه في الجملة نفسها.** موافقة تُسحب والصفحة باقية ليست موافقة.

## الشهادات

```json
{"certificate_id":7,"title_ar":"…","has_image":true,"is_image_public":false,
 "attachment_id":null,"registration_no":null}
```

`attachment_id` يعود `null` ما لم تقل **هذه الشهادة** إن صورتها عامّة، أو يكن المتصل من
المركز أو صاحب الملفّ. الشرط يُقيَّم في القاعدة.

**و`has_image` يبقى `true`** بقصد: أسرة ترى «شهادة بلا صورة» صدق؛ أسرة لا تفرّق بين «لا
صورة» و«صورة ليست لك» تطلب من المركز ما لن تأخذه.

**ونشر الصورة نقطة مستقلّة** لأنه قرار مستقلّ. حقلًا في تعديل عام كان يركب مع تصحيح
إملائي، فيَنشر مَن يصحّح حرفًا وثيقةَ هويّة دون أن يقرأ ما بجانبه.

# المستخدمون والأدوار والصلاحيات

الآليّة التي تُوزَّع بها كل صلاحية أخرى. **ولا قاعدة تُفحص في المعالِج** — الهجرة 0036
تحملها كلها.

```
GET    /api/v1/users            ?q&status&role&archived&page&limit
POST   /api/v1/users            {username, full_name_ar, user_type, mobile?, branch_id?}
PATCH  /api/v1/users/{user_id}  {full_name_ar?, mobile?, status?, clear_mobile?}
DELETE /api/v1/users/{user_id}  ?restore=true
PUT    /api/v1/users/{user_id}/roles  {role_codes:[...]}
GET    /api/v1/roles                  ← الأربعة وصلاحيات كلٍّ منها متداخلة
GET    /api/v1/roles/{code}/permissions
GET    /api/v1/permissions
```

**لا كلمة مرور في أي مسار.** الحساب يُنشأ بلا واحدة والرد يقول ذلك: `has_password:false`.
حقلُ كلمة مرور على شاشة إنشاء هو كلمة مرور تُقال بصوت وتُكتب على ورقة.

**والمنح فعل مسجَّل**: `granted_by` و`granted_at`. «مَن أعطى هذا الشخص صلاحية الفواتير،
ومتى» أوّل سؤال يُطرح بعد أن يقع شيء.

**قائمة كاملة لا فروقًا.** مفتاح `role_codes` غائب يأخذ `400`؛ قائمة **فارغة** مقبولة
ومعناها «بلا أدوار». لو تعاملا واحدًا، شاشة نسيت الحقل تسحب صلاحيات أحدهم بصمت.
والقائمة كلها أو لا شيء: دور مجهول يأخذ `400 NO_SUCH_ROLE` **ويُسمّى**، والنصف الصحيح
لا يُطبَّق.

**ولا أحد يغيّر أدواره هو** (`409 NOT_YOUR_OWN_ROLES`) **ولا يؤرشف نفسه**
(`409 NOT_YOURSELF`). الأولى لا فائدة منها اليوم — المدير يملك كل شيء — وتصير السطر
الوحيد الذي يمنع ترقية ذاتية يوم تُمنح `USER.MANAGE` لدور أضيق.

**واسم المستخدم ونوعه غير قابلين للتعديل**: تغيير الاسم يُيتّم كل صفّ تدقيق يسمّيه،
وتغيير النوع يحوّل أسرة إلى موظّف.

**والقائمة مقيَّدة بـ`USER.MANAGE` داخل الاستعلام.** بدونها كان أي مستخدم مصادَق يقرأ
دليل الموظّفين كاملًا — السياسة الأساسية على `hbh.users` تسمح بذلك وتعتمد عليها قراءات
أخرى. بلا الصلاحية: **قائمة فارغة لا رفض**.

# أوليـاء أمر الطفل

```
GET /api/v1/children/{child_id}/guardians
```

**الترتيب كلّيّ**: `is_primary_flg DESC` ثم `created_at` ثم `guardian_id`. الكرت المطبوع
يحمل رقمَي طوارئ على ظهره، ورقمٌ مأخوذ من قراءة غير مرتَّبة هو رقم قد يخصّ أسرة أخرى —
على بطاقة لا يستطيع حاملها التحقّق منها.

والهجرة 0032 تجعل الحدّ الأول قاطعًا وحده (وليّ أمر أساسيّ واحد لكل طفل)؛ والحدّان
الباقيان يغطّيان ما لا يغطّيه الفهرس: **أكثر من وليّ أمر غير أساسي**.

`has_account` موجود لأن أسرة حوّلها `convert_enrolment` لا حساب لها.

# الفواتير — لوحة المركز

```
GET /api/v1/billing/summary
GET /api/v1/billing/ledger   ?kind=payments|packages|balances&page&q
GET /api/v1/dashboard/metrics
```

**`403` لا قائمة فارغة**، خلافًا للشكل المستعمل في بقيّة الخدمة. شاشة فواتير فارغة
**تُقرأ «المركز لا يُدان بشيء»**؛ وموظّفٌ لا يحقّ له رؤية الأرقام يُضلَّل برقم بدل أن
يُقال له إنه لا يراها — ولا شيء يُفشى بالرفض، فكل مركز له فواتير.

**وحجم الصفحة يقرّره الخادم** (٢٥). متصلٌ يسمّيه يستطيع طلب الدفتر كله في نداء واحد،
وهذا مدخل آخر بتكلفة أخرى لم يراجعها أحد.

و`kind` قائمة سماح تختار أحد ثلاثة استعلامات مكتوبة هنا — وأي شيء آخر `400`، لا اسم
يصل إلى SQL.

ملاحظة سريرية.

# الإشعارات

```
GET  /api/v1/notifications                  ?limit&offset
POST /api/v1/notifications/{notification_id}/read
```

**مسار واحد للجمهورين.** `hbh.notifications` تحمل إشعارات الأسرة وإشعارات الموظّفين
معًا منذ الهجرة 0089، والسياسة عليها `user_id = hbh.current_user_id()` — فالمسار يرجّع
صفوف صاحب الجلسة وحده، وليّ أمر كان أو أخصائيًّا. مسار ثانٍ للكونسول كان سيصير نسخة
ثانية من القاعدة نفسها.

**ولا مسار يُنشئ إشعارًا.** الإشعارات تكتبها مشغّلات على الأحداث التي تستحقّ — تقرير
نُشر، موعد تأكّد أو أُلغي، فاتورة صدرت — وهذا تصميم 0015: الأسرة تُخبَر لأن شيئًا
**وقع**، لا لأن معالِجًا تذكّر. ومسار إنشاء كان سيصير أيضًا قدرة «أرسِل ما شئت إلى من
شئت»، وهي منتج آخر بقواعد إساءة أخرى.

الرد: `{rows, unread, total}`. `unread` محسوب على **كل** الصفوف لا على الصفحة —
شارة تقول «٣» لأن ثلاثة غير مقروءة اتّسعت للصفحة الأولى شارةٌ تكذب عند الرابع.

`POST .../read` يرجّع `204`، و`404` لصفّ ليس للمنادي **أو مقروء سلفًا أو غير موجود** —
الثلاثة جواب واحد عمدًا، وإلّا أكّد المسارُ وجودَ إشعار أسرة أخرى لمن يجرّب الأرقام.

**وحالة القراءة حالة واجهة فقط.** لا قاعدة عمل واحدة تقرأ `read_at`: التقرير منشور
فُتح إشعاره أو لم يُفتح.

# تسليم الرسائل

لا مسار HTTP هنا، وهذا هو المقصود. الطابور `hbh.sms_outbox` يملؤه مشغّل على
`hbh.notifications`، ويسحب منه عاملٌ داخل خدمة الـ API عبر `hbh.claim_sms` —
ولا دالّة منها مربوطة بمسار. أضف إلى ذلك أن `hbh.assert_sms_worker` ترفض النداء من
اتصال تحمل هويةَ مستخدم، فحتى مسار يُضاف سهوًا لا يصل الطابور.

المراقبة عبر `hbh.v_sms_delivery` (الرقم مقنّع، ولا نصّ لرسالة رمز دخول أصلًا) لمن
يملك `OPS.VIEW`.

## رموز الأخطاء العامة

| الرمز | الحالة | متى |
|---|---|---|
| `VALIDATION` | `400` | جسم غير صالح · حقل مجهول · رقم لا يطابق النمط · **قيد في السكيما رفض الجسم** |
| `UNAUTHENTICATED` | `401` | بلا توكن · توكن مزوّر · مُلغى · منتهٍ · حساب أُوقف · كوكي بثّ ميتة |
| `FORBIDDEN` | `403` | يرى الشيء ولا يملك التصرّف — **بعد أن ثبت أنه يراه**، فلا يؤكّد وجود شيء جديد |
| `NOT_FOUND` | `404` | غير موجود، **أو لا يحقّ لك** |
| `METHOD_NOT_ALLOWED` | `405` | مع ترويسة `Allow` تسمّي **كل** ما يقبله المسار |
| `ALREADY_LOGGED` | `409` | اليوم مسجَّل — ولا يُكتب فوقه |
| `NOT_LIVE` | `409` | الجلسة ليست جارية |
| `RATE_LIMITED` | `429` | تجاوز حدّ مسارات الدخول |
| `INTERNAL` | `500` | السبب في اللوج مع `request_id`، ولا يخرج للعميل أبدًا |
| `UNAVAILABLE` | `503` | `/readyz` فقط |
| `STREAM_UNAVAILABLE` | `503` · `502` | لا بوّابة وسائط صالحة · أو بوّابة لا تُجيب |

**`400` لا `500` حين يرفض قيدٌ في السكيما جسمًا سليم الشكل.** الرفض خطأ المتصل، و`500`
كانت ستلوم الخادم على قاعدة كسرها العميل — وتدفن، في كومة أخطاء داخلية، اليوم الذي
يتعطّل فيه شيء حقًّا.

`INTERNAL` لا يحمل نصًّا. نصّ خطأ داتابيز يصل إلى متصفّح هو كشفٌ للسكيما.

## ما تفرضه الطبقة، وما لا تفرضه

**تفرضه هنا:**
شكل المدخلات · حدّ معدّل على مسارات الدخول بعنوان المتصل · ترويسات الأمان ·
`CORS` بقائمة سماح **مطابِقة تمامًا** بلا حرف بدل · تسجيل المحاولات والقراءات الحسّاسة.

**لا تفرضه هنا إطلاقًا:** من يرى ماذا.
كل معاملة تبدأ بـ `set_config('hbh.user_id', …, true)` ثم تسأل، والسياسات تجيب.
شرطٌ إضافي في المعالِج كان سيصير نسخة ثانية من قاعدة، والنسختان تختلفان في النهاية —
**والأضعف هي التي تقرّر**.

**حدّ المعدّل ليس تكرارًا للداتابيز:** `request_otp` تكبح حسابًا واحدًا، لكنها لا تكبح
متصلًا يمشي على قائمة أرقام بمحاولة لكل رقم — كل طلب هو الأول لحسابه. هذه هي الفجوة،
ولهذا المفتاح هو عنوان المتصل لا رقم الجوّال.
