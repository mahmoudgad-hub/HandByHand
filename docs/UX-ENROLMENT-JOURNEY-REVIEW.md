# رحلة الالتحاق — مراجعة تنفيذية وترتيب الإصلاح

2026-09-14 · نطاق هذه المتابعة: مراجعة رحلة الالتحاق التي اقترحنا البدء بها. لا تغييرات Frontend أو Backend أو بيانات تشغيلية.

## النتيجة الحاسمة

هناك ثلاثة أشياء مختلفة يجب ألا تختلط:

1. **الموجود:** تقديم مجهول ينشئ طلبًا؛ التحويل بعد التواصل ينشئ ملف المستفيد ويربط ولي الأمر ويمنح حساب البوابة.
2. **قرار المالك المسجل OD-01:** التقديم بعد التحقق من الجوال يطابق الأسرة والمستفيد وينشئ الناقص فقط؛ لا يمنح حساب دخول بمجرد التحقق.
3. **الخلل العاجل R01:** الواجهة تقترح «تسجيل حجز التقييم» دون حقل تاريخه، والـAPI لا يستقبله، بينما قاعدة البيانات تشترطه. وحتى إضافة التاريخ وحده لا تنشئ موعدًا في جدول المركز.

لذلك لا نعتمد «التحويل أولًا ثم الحجز» كتغيير نهائي للرحلة؛ هو خيار مسموح في النظام الحالي، بينما المسار المستهدف تحكمه قرارات المالك المسجلة.

**فرع التقييم السريري:** جدول assessments ودواله لا يقابلهما API تشغيلية في server.go الحالي. «تم حجز المقابلة» لا تعني «أُجري تقييم» أو «نُشرت توصيات». لا نعرض نجاحًا أو تقرير تقييم من خانة ملاحظة.

الفوترة والخطة مساران مرتبطان بالمستفيد حسب العملية. لا أثبت هنا أن السداد شرط لكل جلسة أو أن الخطة شرط لكل حجز؛ لا يستنتج شرط عمل من ترتيب جدول UX.

## بطاقة جاهزة لفريق الخلفية: R01

**المشكلة:** ENROLMENTS_SPEC يعرض انتقالًا لا يمكن للعميل استيفاء حقل مطلوب له في قاعدة البيانات.

**نطاق الإصلاح المقترح للمراجعة:** توفير قراءة/كتابة التاريخ المتفق عليه للمقابلة عبر عقد موثق، مع تحقق الخادم وتحديث ذري للحالة والتاريخ. يُحافظ على الطلبات القديمة وعلى بقية انتقالات الحالة دون تاريخ عندما لا تتطلبه. لا تعديل للمهاجرة 0110 التاريخية ولا إسقاط لقيدها. إذا أضيف ربط Appointment في نفس المرحلة فيجب أن يأتي من API حجز فعلي، لا من إنشاء عمود تاريخ فقط.

**التوافق:** لا تغير معنى convert أو submit القديم لمجرد إصلاح هذا الحقل. مسار التقديم الجديد والتفعيل مرتبطان OD-39؛ لا يفعّل التحقق الإلزامي قبل جاهزية الواجهة واختبار مسار التوافق. تحقق مرسل لكنه فاسد لا يُقبل كطلب مجهول بديل.

**الاستجابة:** الرسائل تفرق بين رفض بيانات الموعد، عدم صلاحية، تعارض، وفشل الاتصال. لا نحدد HTTP code جديدًا أو payload نهائيًا دون مراجعة عقود الخدمة؛ يُعاد استعمال اصطلاحاتها الحالية.

## سيناريوهات القبول المطلوبة لاحقًا

| Scenario | Expected |
| --- | --- |
| تقديم حالي صحيح | application_no؛ لا وعد بملف/حساب فوري |
| فتح طلب NEW ثم إغلاقه | يبقى NEW |
| تواصل مصرح ومؤكد | CONTACTED مع الملاحظة المناسبة |
| انتقال مقابلة بلا تاريخ | رفض واضح؛ لا حالة ناجحة أو إشعار نجاح وهمي |
| تاريخ صالح في العقد المصحح | يحفظ UTC ويعرض بتوقيت المركز؛ الرقم/التاريخ واضحان |
| تسجيل تاريخ فقط دون Appointment | لا تسمه حجز فتحة على جدول المركز |
| تحويل من CONTACTED | يحافظ على السماح الحالي؛ لا Assessment شرط إضافي |
| تحويل من NEW أو محاولة تحويل مكرر | يرفض وفق قاعدة الخادم؛ لا ملف مكرر |
| فشل منح حساب أثناء التحويل | لا نجاح جزئي في التحويل |
| تحويل ناجح | فتح ملف المستفيد بالمعرف المعاد؛ موافقة البث لا تمنح تلقائيًا |
| مهمة إسناد مستفيد معين | نفس المستفيد في الحوار؛ لا انتقال لقائمة بلا سياق |
| موظف عرض بلا حق كتابة | لا CTA كتابة متاح؛ رفض الخادم يظل الضابط |
| طلب خارج أول صفحة | يظهر أو تعرض حدود القراءة؛ لا «لا طلبات» كاذبة |
| تحقق جديد صحيح ثم إعادة إرسال | مطابقة/إعادة استخدام طبقًا للعقد؛ لا طفل أو طلب مكرر |
| تحقق جديد فاسد مع مسار توافق فعال | لا سقوط صامت إلى submit المجهول |
| أسرة موثقة بلا حساب بوابة | التحقق وحده لا يفتح البوابة |

هذه معايير قبول وليست نتائج اختبارات شُغّلت. فحص هذه المتابعة كان قراءة للمصادر والقرارات؛ لم يشمل تطبيق مهاجرات أو إرسال OTP/SMS أو تعديل طلبات.

## نقطة البداية التالية

حزمة Frontend الأولى: J-01 وJ-02، مع J-03 ضمن حدود العرض. حزمة الخلفية: مراجعة R01 مقابل OD-01 أولًا، حتى لا يُنفذ حقل تاريخ ثم يعاد بناء الرحلة دون خطة توافق. لا إعادة تصميم شاملة أو إضافة شاشات انتظار لحل هذه الفجوة.
